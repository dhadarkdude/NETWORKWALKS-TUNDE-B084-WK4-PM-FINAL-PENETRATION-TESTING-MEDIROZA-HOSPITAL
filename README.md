# Penetration Testing — Mediroza General Hospital

A full black-box penetration test completed as part of the NetworkWalks Cybersecurity and Ethical Hacking internship, Week 4. Covers reconnaissance, SQL injection and authentication bypass, password cracking, and discovery of an unauthenticated database backup exposure, written up as a complete professional penetration testing report.

## Project Overview

NetworkWalks assigned a 5-day black-box engagement against a training target, `medirozahospital.com`, a fictional hospital built specifically for this exercise. The brief was structured as 4 milestones: gain initial access and retrieve 3 confidential patient PDF lab reports, crack the encryption protecting them, dig deeper to find a critical data exposure on the server, and write it all up as a formal pentest report. Everything in this repo, including the staff and shareholder data shown below, is synthetic training data generated by NetworkWalks for this lab. No real people, patients, or organizations are involved.

## Objectives

- Perform reconnaissance against the target to map its infrastructure and content
- Identify and exploit a vulnerability to gain unauthorized access to confidential data
- Recover the contents of encrypted files obtained during the engagement
- Identify a deeper, critical data exposure on the server
- Produce a complete professional penetration testing report

## Scope & Rules of Engagement

- **Target:** https://medirozahospital.com
- **Type:** Full black-box penetration test
- **Duration:** 5 days
- **Authorization:** Written authorization provided by NetworkWalks Academy
- **Rules:** Testing limited to the target domain only. No social engineering. No denial-of-service testing. Work performed independently.

## Tools Used

- `whois`, `nslookup`, `whatweb`, `curl`, `wafw00f`, `dnsrecon` — reconnaissance and fingerprinting
- `gobuster` — content/directory discovery
- Manual browser testing — login form and SQL injection testing
- `pdf2john`, John the Ripper (`rockyou.txt`) — PDF password recovery
- `exiftool` — document metadata analysis
- `grep` / `sed` — SQL backup analysis

## Phase 2 (Milestone 1): Initial Access via SQL Injection

The Patient Portal (`/patient/login.php`) explicitly stated: *"Sign in to view your lab reports and results"*, making it the target for retrieving the 3 confidential PDF files.

**Step 1 — Confirm the injection point.** A single quote in the Username field returned a raw PHP/MySQL error:

![Single quote test result](./single%20quote%20outcome.png)

This confirmed the login query concatenates user input directly into SQL with no sanitization or parameterized statements.

**Step 2 — Baseline tests (non-injection).** Before exploiting it, plausible usernames were tried normally to rule out simple credential guessing:

![Trying admin as a normal patient username](./trying%20admin%20as%20patient%20username.png)
![Trying a random staff login](./trying%20random%20staff%20access.png)

**Step 3 — Authentication bypass payload testing.** Several SQL injection payloads were tested in sequence against the Username field:

![First payload attempt](./first%20sql.png)
![Second payload attempt](./second%20sql.png)
![Third payload attempt](./third%20sql.png)
![Fifth payload attempt](./fifth%20sql%20attempt.png)

Each of these returned either a SQL syntax error or a "Username not found" response, useful for documenting the query's structure, but none logged in.

**Step 4 — The successful payload.**

```
Username: admin' -- 
Password: (left blank)
```

![Successful authentication bypass payload](./fourth%20sql.png)

This worked because the trailing `-- ` comments out the rest of the query, including the password check, and because an account aliased or named `admin` genuinely exists in the patient table.

**Step 5 — Access granted.**

![Patient Portal access granted, listing 3 confidential reports](./fourth%20attempt%20with%20admin.png)

This single injection point granted full, unauthenticated access to 3 confidential, password-protected PDF lab reports: **Pathology Report — S. Dlamini** (LR-2024-1187), **Pathology Report — P. Reddy** (LR-2024-1192), and **Pathology Report — E. Thompson** (LR-2024-1205).

## Phase 3 (Milestone 2): Cracking the Encrypted Reports

All 3 retrieved PDFs were password protected. Hashes were extracted and attacked offline.

```bash
pdf2john patient_report_1.pdf > patient1hash.txt
pdf2john patient_report_2.pdf > patient2hash.txt
pdf2john patient_report_3.pdf > patient3hash.txt

john --wordlist=/usr/share/wordlists/rockyou.txt patient1hash.txt
john --wordlist=/usr/share/wordlists/rockyou.txt patient2hash.txt
john --wordlist=/usr/share/wordlists/rockyou.txt patient3hash.txt
```

![Hashing all 3 PDFs](./hashing%20all%203%20pdfs.png)
![Patient 1 cracked](./patient1%20cracked.png)
![Patient 2 cracked](./patient2%20cracked.png)
![Patient 3 cracked](./patient3%20cracked.png)
![All 3 passwords recovered](./all%20password%20of%203%20pdfs.png)

| File | Password |
|---|---|
| `patient_report_1.pdf` | `123456` |
| `patient_report_2.pdf` | `password` |

All 3 passwords were trivial dictionary values, cracked in under a second each against `rockyou.txt`, despite the PDFs using 128-bit encryption. The encryption algorithm wasn't the weakness, the password choice was.

## Phase 4 (Milestone 3): Unauthenticated Database Backup Exposure

**Step 1 — Dead end: PDF metadata.** As a parallel lead, document metadata was checked for hidden clues:

```bash
exiftool patient_report_1.pdf
```

![Exiftool outcome](./exiftool%20outcome.png)

Came back clean, no hidden paths or author data. Not the right trail.

**Step 2 — The real lead: `/old/`.** `robots.txt` had disallowed `/old/` alongside `/patient/` and `/staff/`. It had never actually been visited:

```bash
curl -L https://medirozahospital.com/old/
```

![Directory listing at /old/](./curl%20of%20the%20old%20path.png)

Directory listing (autoindexing) was enabled, exposing a single file with no authentication required: **`mediroza_db_backup_2019.sql`**.

**Step 3 — Analyze the backup.**

```bash
curl -O https://medirozahospital.com/old/mediroza_db_backup_2019.sql
grep -i "CREATE TABLE" mediroza_db_backup_2019.sql
```

![SQL dump table structure](./old%20sql%20database.png)

Two tables: `staff` and `shareholders`.

```bash
sed -n '/CREATE TABLE `staff`/,/);/p' mediroza_db_backup_2019.sql
sed -n '/CREATE TABLE `shareholders`/,/);/p' mediroza_db_backup_2019.sql
grep -i "INSERT INTO \`staff\`" mediroza_db_backup_2019.sql
grep -i "INSERT INTO \`shareholders\`" mediroza_db_backup_2019.sql
```

## Risk Analysis

| Finding | Risk Level | Affected Area |
|---|---|---|
| SQL injection leading to full authentication bypass | **Critical** | `/patient/login.php` |
| Unauthenticated, public database backup exposure | **Critical** | `/old/mediroza_db_backup_2019.sql` |
| Exposure of staff PII (national IDs, salaries, contacts) | **Critical** | `staff` table (30 records) |
| Exposure of shareholder/ownership structure | **High** | `shareholders` table (10 records) |
| Weak, dictionary-crackable PDF passwords | **High** | `patient_report_1/2/3.pdf` |
| Directory listing enabled on production server | **Medium** | `/old/` |
| Verbose SQL error messages shown to end users | **Medium** | `/patient/login.php` |
| Predictable legacy/user-enumeration paths | **Low** | `~admin`, `~root`, `/old/`, etc. |

## Recommendations

- **SQL Injection:** Use parameterized/prepared statements everywhere; never concatenate user input into SQL.
- **Backup Exposure:** Remove backups from any web-accessible directory immediately; store outside the webroot; disable directory listing server-wide.
- **PII/Shareholder Exposure:** Treat as a reportable data breach; notify affected parties per applicable data protection law; rotate any exposed credentials.
- **Weak PDF Passwords:** Generate random, non-dictionary passwords for sensitive documents.
- **Directory Listing:** Disable autoindexing across the entire server, not just discovered paths.
- **Verbose Errors:** Disable error display in production; log errors server-side instead.

## Problems Encountered & Solutions

The PDF metadata check (exiftool) was a dead end, no hidden paths or clues there, which was a useful reminder not to assume every lead pans out. The real lead came from going back to an unexplored item from the original `robots.txt` scan (`/old/`) rather than a new tool or technique, methodical revisiting of earlier recon data mattered more than finding a new attack surface.

## What I Learned

- A single unsanitized input field can cascade into full compromise of a sensitive data store.
- `robots.txt` is a map of what an organization wants hidden, not a security control, it often points an attacker straight at the most sensitive paths.
- Strong encryption (128-bit PDF encryption) is meaningless if the password protecting it is weak and dictionary-common.
- A forgotten backup file in a misconfigured directory can expose more data than a direct application exploit.
- Methodical reconnaissance and revisiting earlier findings matters as much as finding new vulnerabilities.
